# Progress checkpoint — 11 November 2026

Status: design/discovery; no working resolver or validated ontology release. This is a curated session record, not a verbatim transcript.

## Purpose and settled direction

Agent Role Ontology is intended as a harness-neutral discovery, routing, and team-composition layer, not another prompt library. Canonical roles specify responsibilities, inputs, outputs, boundaries, and observable acceptance criteria without prescribing vendors, operating systems, tools, or stacks. Domain and technology specialisations remain explicit facets.

Upstream repositories supply replaceable prompt implementations. Proposed flow: task and constraints -> role discovery -> team composition -> implementation selection -> pinned retrieval -> inspection -> conversion -> validation -> staged activation -> evaluation. The ontology supplies meaning; the registry supplies candidates; the resolver applies policy; adapters translate formats; harnesses execute. These components are planned, not implemented.

## Model boundaries

Distinguish function, role, capability, domain, technology, method, workflow, artifact, versioned definition, deployment profile, execution, and evaluation. Keep canonical role IDs separate from runtime agent names and upstream identifiers. Declared capabilities are not demonstrated capabilities. Filename similarity is not semantic equivalence. Identical prompts can have different permission profiles.

## Dependencies and surprises

Implementation records must disclose required software, versions, OS/shell/path assumptions, services, accounts, costs, credentials, privileges, network/data handling, supporting files, and harness-specific features. Record mandatory/optional/conditional requirements, evidence, source revision, and whether observations are declared, inferred, or tested. Unknown is a valid state. Apply hard compatibility and user-policy constraints before ranking candidates. Never silently escalate permissions, run upstream installers, or treat imported prompt text as installer instructions.

Conversion is not portability: model aliases, tools, relative references, orchestration instructions, and proprietary-service dependencies can remain incompatible after syntax conversion. Capture adapter version, source revision, target version, validation results, and semantic losses. Trending sources are discovery candidates, not automatic endorsements or upgrades.

## Session context

The user curated Kilo marketplace, wshobson/agents, and VoltAgent/awesome-claude-code-subagents definitions. Wshobson artifacts were installed for OpenCode and converted with Rulesync; VoltAgent artifacts were staged and unique-filename additions copied. Filename uniqueness did not establish semantic uniqueness. Current upstream content and exact local transformations have not been fully inventoried in this repository.

Earlier guidance incorrectly asserted that nested agent directories prevented discovery. Inspection of Kilo v7.8.27 found recursive Markdown discovery and frontmatter name overrides. Agent-list output also prints expanded permissions. These are observations from session source inspection, not a newly executed integration test. The installed files were not inspected directly from the user's filesystem. Reverify version-specific behaviour before automation.

## Collaboration

Prefer existing standards and tools over custom software. Conceptual design, ambiguous mappings, and evidence review can happen in the research conversation. Local agents should execute bounded inventory, hashing, extraction, validation, and approved patch tasks. Auto-routed models must be supported by deterministic checks, small tasks, evidence, and escalation rather than assumed semantic reliability. No autonomous acceptance of mappings or live deployment changes.

## Candidate reuse, not adopted architecture

Evaluate SKOS for concepts/mappings, PROV-O for provenance, LinkML for schemas/validation/export, Rulesync for supported conversions, and A2A for alignment with remote-service discovery. Do not assume every source/target harness pair is supported. No graph database, custom package manager, converter, or orchestrator is approved merely by this checkpoint.
